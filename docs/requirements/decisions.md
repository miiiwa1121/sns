# 重要決定事項 (Decisions)

本ドキュメントでは、OmniPulse AI Studio プロジェクトにおいて合意・決定された重要事項（ADR: Architectural Decision Records 相当）を記録する。

## Decision 001: 対象プラットフォームと動画フォーマット戦略
- **決定日**: 2026-10-08
- **決定内容**:
  - **対象プラットフォーム**: YouTube (Shorts & 長尺)、TikTok、Instagram (Reels)、X (Twitter) の4媒体。
  - **フォーマット**: YouTube向け長尺動画（10分前後）をマスターとして制作し、感情の高まりや重要ポイントをAIが自動検出し、30〜60秒の縦型ショート動画（9:16）に切り抜いて各SNSへマルチ投稿する。
- **背景・理由**:
  - 2026年のアルゴリズム動向において、ショート動画単体よりも「ショートから本編長尺動画への誘導」が可能なアカウントがプラットフォームから最も高く評価されるため。

## Decision 002: 自律運用の形態（半自律型からの立ち上げ）
- **決定日**: 2026-10-08
- **決定内容**:
  - 完全無人自律（Auto-Pilot）ではなく、まずは人間がダッシュボード上で企画・台本・プレビューを確認し、ワンクリックで承認・配信できる「半自律・承認制（Human-in-Loop）」として稼働させる。
  - 将来的にワンクリックで完全自律運用へ切り替えられるトグル設計を維持する。
- **背景・理由**:
  - 初期段階での誤投稿や品質ブレを防ぎ、実際にPDCAが回るか人間が確認しながら検証を進めるため。

## Decision 003: 技術スタック選定
- **決定日**: 2026-10-08
- **決定内容**:
  - フロントエンド / バックエンド: **Next.js (App Router, TypeScript)**

## Decision 004: AIモデルの選定と検証フェーズの運用方針
- **決定日**: 2026-10-08
- **決定内容**:
  - **検証フェーズ（現在）**: 外部API契約を急がず、現在のAIエージェント（Antigravity / Gemini 3.8 Flash）が直接各フェーズ（リサーチ、長尺台本、切り抜き、分析）の頭脳を担う。費用0円でプロジェクトのPDCAが回るか実証する。

## Decision 009: データの真正性と配信APIの安全方針
- **決定日**: 2026-10-09
- **決定内容**:
  - **架空データを DB に書かない。** 実測値が無い分析・未実装の工程は、架空の数値や結論で補わず、エラー（400 / 501）として返す。CriticAI の診断は実測値から計算できる事実だけを書く。
  - **投稿していないものを「成功」と記録しない。** 認証未設定・未実装・API エラーはすべて `PublishLog.status = "failed"` とし、理由を `errorMessage` に残す。偽の投稿URLは作らない。
  - **配信は「このプロジェクトのレンダリング済みショート」だけを対象にする。** 固定ファイルは使わない。配信済みのプラットフォームには再送しない。
  - **配信系 API はローカル専用。** 開発サーバーは `127.0.0.1` にバインドする。書き込み系 API は同一オリジンかつ JSON ボディのみ受け付ける（CSRF 対策）。CRON API は `INTERNAL_API_TOKEN` を必須とする。
- **背景・理由**:
  - コードレビュー（2026-10-09）で、シミュレーション投稿が成功扱いになる・架空の再生数から学習知見が作られる・同じ Wi-Fi の第三者が配信 API を叩ける、といった問題が見つかった。実アカウント「ついていくのが精一杯」の運用前に、データと投稿の信頼性を確保するため。

## Decision 010: エージェント自律運用の検証範囲
- **決定日**: 2026-10-09
- **決定内容**:
  - **検証の目的**: エージェント（Claude Code セッション）が、リサーチ → 台本 → 音声 → 動画 → 投稿 → 計測 → 分析を自分で回せるかを確かめる。エージェントは CLI（`npm run agent`）で各工程を操作する。手順は `docs/operations/agent-runbook.md`。
  - **動画はショート（9:16、30〜50秒）単体から始める。** 長尺マスターから切り抜く方式（Decision 001）は、ショート単体のサイクルが回ってから着手する。
  - **リサーチは出典必須。** Web 検索で一次情報を含む出典を集め、出典の無い話題は登録できない。検索ボリュームなど測っていない数値は入れない。
  - **自動投稿は YouTube のみ。** 他3媒体は、動画とキャプションを書き出してユーザーが手動で投稿し、URL を記録する。
    - TikTok: Direct Post は審査前だと非公開投稿に限られる。
    - Instagram: 動画を公開URLでホストする必要がある。
    - X: 動画投稿 API の実装と、API プランの確認が必要。
  - **YouTube への投稿は既定で非公開（private）。** 未審査の API プロジェクトからの投稿は非公開に固定されるため。公開はユーザーが YouTube Studio で切り替える。
  - **公開承認は人間が行う（Decision 002 を維持）。** エージェントはプレビューを見せて明示的な OK を得てから `approve` を実行する。
  - **Project.stage は、1媒体でも配信されたら `published` にする。** 自動投稿が YouTube のみのため、4媒体そろうまで待つと状態が進まない。
- **背景・理由**:
  - 各SNSの API 制約の中で、まず「エージェントが自分で回せる範囲」と「人手が必要な範囲」を実測で切り分けるため。人手が必要な箇所は runbook に一覧化し、自律化の課題として扱う。

## Decision 011: ショート動画のデザインと声
- **決定日**: 2026-10-10
- **決定内容**:
  - **画面は白と水色を基調にしたシンプルなデザイン**にする。
  - **絵文字・スタンプは使わず、UI 部品で表現する**（チャット画面の再現・ステップ・チップ・選択UI・比較カード）。
  - チャット画面は特定サービスの UI を使わない汎用の再現にし、「※イメージ」と表示する。
  - 声は **VOICEVOX のずんだもん（ノーマル、速度 1.15）**。クレジット「VOICEVOX:ずんだもん」を動画内と投稿文に入れる。
  - **BGM は使わない**。行の切り替えに自作の効果音だけを入れる。
  - マスコット（アイコンの汗だくキャラ）は画面左下に常駐させ、行ごとに表情を変え、声に合わせて口を動かす。
  - 動画ごとの構成を絵コンテとして `docs/videos/` に自動で記録する。
- **背景・理由**:
  - 第1弾の初版（暗い背景に字幕枠だけ、edge-tts、効果音なし）について、ユーザーから「クオリティが低い」との評価を受けた（映像・音・構成・デザインのすべて）。改善後、ユーザーが配色と表現方法を指定した。
  - テンプレートの仕様は `docs/architecture/video-template.md`。

## Decision 013: 生成物は `data/` に集約し、`agent/`・`remotion/` をルート直下に置く
- **決定日**: 2026-10-10
- **決定内容**:
  - 動画・音声・作業ファイル・依頼ジョブのログなどの生成物は `data/`（git 管理外）に置く。企画ごとに `data/projects/<id>/` にまとめ、片付けはフォルダごと消すだけにする。`public/` は固定素材（`brand/`・`se/`）だけにする。
  - DB の `ShortClip.renderedFilePath` は `data/` からの相対パス（`projects/<id>/video.mp4`）を保存する。
  - 動画の配信は `public/` ではなく Route Handler `/api/media/[...path]` が行う（動画とサムネのみ）。
  - エージェント CLI を `agent/`、動画テンプレートを `remotion/` としてルート直下に置く。
- **背景・理由**:
  - 生成物が `out/`・`public/audio/`・`public/videos/` に分散し、増え続けても掃除の単位がなかった。`public/` に置くと配信対象に混ざる。
  - Prisma（DB）が持つのは場所だけで、ファイル本体は管理しない。ファイルの置き場を1か所に決めておく必要があった。
  - `agent/`・`remotion/` は Next.js の画面とは別のランタイムで、`scripts/`・`src/` の下では役割が伝わらなかった。
- 詳細: [architecture/directory-structure.md](../architecture/directory-structure.md)

## Decision 014: 運用操作はすべて管理画面で行えるようにする
- **決定日**: 2026-10-10
- **決定内容**:
  - 日々の運用に必要な設定・実行は、管理画面（サービス内）でできるようにする。管理画面でできない運用操作を IDE・ターミナルから実行させるのは NG。
  - ただし本プロジェクトは OSS のため、**最初の環境構築**（`npm install`、VOICEVOX・ffmpeg・Chrome などのツール導入、Google Cloud での OAuth クライアント作成）は、利用者が docs の手順を見ながら自分で行う。画面化はしない。
  - 迷ったときは「運用中に繰り返す操作か」で判断する。繰り返すなら画面に置く。
  - 処理本体は `src/lib/services/` に置き、画面から呼ぶ。CLI は依頼で動くエージェント用の道具で、人の操作手段としては案内しない。
  - 生成物の整理は CLI の `clean` をやめ、「設定」画面（`/settings`）に移した。設定は `AppSetting` に保存する。
- **背景・理由**:
  - 整理を CLI だけで用意したところ、ユーザーから「サービス内で設定できるようにして。サービス内でできないことを IDE 上から実行するのは NG」と指摘された。
- **対応状況**:
  - 2026-10-10: YouTube 連携をアカウント画面のボタンに、OAuth クライアントの ID・シークレットを「設定」画面に移した（CLI の `youtube:auth` は廃止）。
- 原則の範囲は、ユーザーの指摘（「OSS なので、最初の設定くらいはマニュアルを確認しながら自分でやる必要がある」）を受けて、同日に上のとおり絞った。

## Decision 015: 動画の構成案を画面で管理し、アカウントごとに既定を選ぶ
- **決定日**: 2026-10-10
- **決定内容**:
  - 指示書のうち「構成」の部分（尺・行数・流れ・場面の選び方）を **構成案**（`StructureTemplate`）として切り出し、管理画面の「構成案」で追加・編集・削除できるようにする。
  - 編集できるのは構成の部分だけ。コマンド・手順・禁止事項・事実と出典のルールは `agent/job-prompt.ts` に固定する。
  - 構成案は全アカウント共通の一覧。各アカウントは既定を1つ選び、依頼時に選び直せる。
  - 依頼には構成案の名前と本文の写しを保存し、企画には構成案を記録する（あとで構成案ごとに成績を比べるため）。
- **背景・理由**:
  - アカウントによって動画の構成を変えたいが、構成は指示書にコードで固定されていた。
  - 指示書全体を編集可能にすると、承認前に投稿しない・Web の指示に従わないなどの安全装置まで消せてしまう（ユーザーと合意して構成部分に限定）。

## Decision 016: 構成案の相談は Claude Code を「ツールなしの会話相手」として最小構成で呼ぶ
- **決定日**: 2026-10-10
- **決定内容**:
  - 構成案の相談・試作では、Claude Code（`claude -p`）を次の設定で呼ぶ（`src/lib/claude.ts`）: ツールなし（`--tools ""`）、MCP サーバーなし（`--strict-mcp-config`）、設定ファイルなし（`--setting-sources ""`）、短いシステムプロンプト（`--system-prompt`）、答えの形は JSON スキーマで固定（`--json-schema`）。
  - 試作は台本と、ブラウザ上の映像プレビュー（Remotion Player、音声なし）まで。音声合成とレンダリングはしない。
- **背景・理由**:
  - API キーは設定しておらず、動画づくりの依頼と同じく Claude Code を使う。
  - 既定のままでは、既定のシステムプロンプトと接続済みの MCP サーバーの定義を毎回読み込むため、あいさつ1回で約1.5ドル（表示上の金額）かかった。最小構成では約0.01ドル・約1秒（相談は約15秒、試作は約30秒）になった。
  - 相談と試作は何度も繰り返すため、速さを優先した（試作の範囲はユーザーと合意）。

## Decision 017: 話し方・台本のルールはアカウントではなく構成案で決める
- **決定日**: 2026-10-10
- **決定内容**:
  - アカウントの「話し方」「台本のルール」をなくし、構成案の本文に書く。アカウントが持つのは、名前・カテゴリ・コンセプト・視聴者・既定の構成案・SNS ごとのハンドル。
  - アカウントには YouTube 以外（TikTok / Instagram / X）のハンドルも入力できるようにする。
- **背景・理由**:
  - ユーザーの指摘（「構成案で指定することなので、必要ないのでは」）。実際に、チャンネルの台本ルール（専門用語には必ず比喩）と構成案（ちょうど10行）がぶつかることがあった。指示の置き場所を1つにする。
  - 構成案は全アカウント共通のため、話し方はアカウントではなく構成案ごとに決まる。アカウントごとに口調を変えたい場合は構成案を分ける。
- **移行**: 既存アカウントの値は、構成案「標準（30〜50秒）」に話し方と台本のルールを、「構成案構成案」に話し方と冒頭のフックを書き足した（後者は相談で「比喩の決まりを外す」と指示されていたため、比喩のルールは足さない）。

## Decision 018: AI 連携画面で、用途ごとに使う AI とモデルを選べるようにする
- **決定日**: 2026-10-10
- **決定内容**:
  - 管理する AI は Claude Code・Antigravity（今使っているもの）と、Claude API・Gemini API（API キー・従量課金）。
  - 用途は「動画づくりの依頼（既定）」「構成案の相談・試作」「動画編集の手直し」の3つで、それぞれ AI とモデルを選ぶ。（2026-10-11 変更: 依頼の画面で AI を選び直す機能をなくし、動画づくりの依頼も割り当てだけで決める。名前も「動画づくりの依頼」に。dashboard-ui.md 3.16）
  - 依頼は、今は Claude Code と Antigravity だけが対応する。API の AI で依頼を動かすには、Web 検索や CLI の操作をツールとして持たせて作業を進める仕組みが別に要るため、今回は相談・編集（JSON を1回返すだけの用途）に限った。
  - 3つの AI に共通の答えの形（JSON Schema）を `src/lib/ai/schemas.ts` に置く。Claude API の構造化出力は全 object に `additionalProperties: false` が要り、自由な項目を持てないため、場面（scene）は種類ごとの項目を `anyOf` で決めた。Gemini には OpenAPI 形式（`nullable` など）に変換して渡す。
  - Claude API は公式 SDK（`@anthropic-ai/sdk`）の `output_config.format`（`json_schema`）、Gemini は `generateContent` の `responseSchema` を使う。
- **背景・理由**: ユーザーの要望（連携済みの AI を管理する画面）。API キーの AI を使えるようにして、Claude Code が使えない環境や、速さ・費用で選びたい場面に対応する。
- **未確認**: Claude API・Gemini API は API キーが未設定のため、実際の呼び出しは試していない（キーを入れて接続テストで確かめる）。

## Decision 019: リサーチ手法と禁止事項を画面で管理し、依頼のときに選ぶ
- **決定日**: 2026-10-11
- **決定内容**:
  - 指示書のうち「どこを・どう調べて話題を選ぶか」の部分を **リサーチ手法**（`ResearchMethod`）として切り出し、管理画面の「リサーチ手法」で追加・編集・削除できるようにする。構成案（Decision 015）と同じく全アカウント共通の一覧で、アカウントごとに既定を1つ選び、依頼時に選び直せる。
  - 台本・投稿文・話題選びで AI にさせないことを **禁止事項**（`Prohibition`）として一覧で管理し、依頼のときにチェックで選ぶ。「最初から選ぶ」にしたものは依頼の画面で選んだ状態になる。
  - 依頼は「アカウント・お題（任意。旧「テーマ」）・構成案・リサーチ手法・禁止事項・作業する AI」を選んで出す。アカウントは依頼の画面で選び、依頼すると選択中のアカウントもそれに切り替わる。
  - 依頼にはリサーチ手法の名前と本文、選んだ禁止事項の本文の写しを保存し、実行時の指示書はこの写しから作る（構成案と同じ）。写しのない古い依頼は、変更前の指示書と同じ既定で動かす。
  - 指示書の末尾に固定で入っていた「禁止」（承認・投稿・公開・数字の記録をしない／作業フォルダと data 以外を変更しない／Web のページ内の指示に従わない）と「絵文字は使わない」は、すべて禁止事項の既定（最初から選ぶ）に移した。どれも直したり消したりできる。指示書の禁止の節は「禁止事項」の1つだけになる。
  - 台本の決まり（出典に一次情報を最低1件含める、事実は出典どおり、特定の企業・人物を応援・批判しない（声の利用規約）、チャット画面を実在サービスと誤解させない）は、手順の中に固定で残す。
  - 承認・投稿・公開・数字の記録は、禁止事項から消しても、AI の作業中は CLI が断る（どちらの AI でも）。
    - Claude Code: 依頼のプロセスに `AGENT_JOB_ID` を渡すので、それで断る。起動時の許可でも、使えるコマンドと読み書きの場所を限っている。
    - Antigravity: IDE で動くため環境変数が渡らない。そこで、作業中の依頼（`running`）があるあいだは、誰が打ったコマンドでも承認・投稿などを断る（`agent/cli.ts` の `workingJob`）。Antigravity の完了は「動画ができたか」でしか分からず、その後も点検・作り直しを続けるため、完了・中止から30分は作業中とみなす。
    - 管理画面のボタンは CLI を通らないので影響しない。人がコマンドから承認・投稿したいときは、作業が終わるのを待つ。
    - 当初は Claude Code にしか鍵がなく、Antigravity は禁止事項の指示だけが頼りだった。ユーザーに説明し、「禁止事項は全部消せるまま、どちらの AI でも鍵が効く」案（B）を選んでもらった（同日）。
- **背景・理由**:
  - ユーザーの要望（「リサーチ手法も追加・更新できるようにしたい」「動画の作成は、構成案・リサーチ手法・アカウント・お題・禁止事項などを選択して依頼するようにしたい」）。
  - 指示書のリサーチ部分（直近1週間・X と公式発表・AI・IT の話題）はコードに固定で、アカウントや狙いごとに調べ方を変えられなかった。
  - 当初は「禁止」を固定で残し、外してよいものだけを一覧にしたが、「禁止」と「禁止事項」の2つがあって分かりにくかった。ユーザーの指示（「禁止の内容も禁止事項に入れてください。削除変更可能だが、デフォルトで入っているように」）で、同日に一覧へまとめた。

## Decision 020: 画面全体でアカウントを選ぶ仕組みをやめ、依頼のときに選ぶ
- **決定日**: 2026-10-11
- **決定内容**:

## Decision 021: AI マネージャーを、人と OmniPulse Studio のインターフェースとして置く

  - ユーザーに確認して決めたこと（同日）: 構成案などの変更は案まで（「一旦それでいい」。運用しながら見直す）／数字の取得と分析は任せる／やりとりは管理画面と外のチャットの両方／承認・投稿は人の OK を受けて代わりに実行／今の画面は残す。

## Decision 022: 動画づくりの依頼を工程（リサーチ／台本／点検）ごとの AI に分ける
- **決定日**: 2026-10-11
- **決定内容**:
  - 依頼を、リサーチ（Claude Code）→ 台本（Claude Code / Claude API / Gemini API から選ぶ）→ 制作（システム）→ 点検（Claude Code）の順に、工程ごとに別々に AI を動かす形にする。工程ごとの AI とモデルは「AI 連携」で選び、依頼した時点の割り当てを依頼に写して残す。
  - 選べる AI は今すぐ動かせるものだけ。リサーチは Web 検索、点検は画像を見て直す作業が要るため Claude Code に限る。Antigravity は工程の終わりを受け取れないため、依頼から外す。
  - 構成案の相談・試作と動画編集の手直しの AI は、それぞれの画面のチャット欄で選ぶ（AI 連携からは外す）。
  - モデルは必ず入れる（空にできない）。既定は Claude Code・Claude API が `claude-opus-5-5`、Gemini API が `gemini-3.8-flash`。
  - AI もモデルもプルダウンで選び、今使えるものだけを出す（同日、ユーザー指示。入力欄に候補を付ける形では、入っている値に合う候補しか出ず、Opus 5.5 しか選べなかった）。
- **背景・理由**:
  - ユーザーの要望（「構成案の相談・試作、動画編集の手直しは、それぞれの画面のチャット欄から選択可能に」「動画づくりの依頼について細分化して AI を指定できるように」「デフォルトでモデルまで入れる。未記入の状態なし」）。
  - 分け方（リサーチ／台本／点検）と、選べる AI を今動くものに限ることは、ユーザーに確認して決めた。API の AI にリサーチや点検をさせるには、Web 検索や画像の入力を別に作る必要があり、API キーも未設定で試せないため。
  - 台本を JSON の1回の答えにしたことで、Claude Code 以外の AI でも台本を書ける。登録（`project:create`）はシステムが行うので、形の検査はこれまでどおり CLI で効く。
- **確認**: 台本の工程だけを Claude Code（`claude-opus-5-5`）で1回試し、形の正しい台本（13行）が36秒で返ることを確かめた。リサーチ・点検を含めた依頼の全体は、まだ通しで試していない。

## Decision 023: 制作（音声合成とレンダリング）は AI を使わない工程として見せ、声・速さ・BGM を画面で選ぶ
- **決定日**: 2026-10-11
- **決定内容**:
  - 動画づくりの依頼の「制作」は、引き続き AI を使わずシステムが行う（台本にどの場面をどう使うかまで書いてあり、判断がないため）。
  - AI 連携の工程の表に「制作」の行を置き、声（VOICEVOX / Edge）・話す速さ・BGM を選べるようにする（`AppSetting.produceVoice` / `produceSpeed` / `produceBgm`）。
  - **同日変更**: 制作の設定は AI 連携ではなく「作成する」で依頼ごとに選ぶ（ユーザー指示）。既定は「おまかせ」で、台本の担当 AI が内容に合わせて選択肢の中から選ぶ（ユーザーが選択）。`AppSetting` の produce* はなくし、既定は `DEFAULT_PRODUCE`（ずんだもん・1.15倍・BGM なし）に。
  - 依頼には依頼した時点の設定を写し、作った動画にはそのときの設定を残す。作り直しは同じ設定で行う（指定がなければ、動画の設定 → 既定 の順）。
  - 環境変数 `AGENT_VOICE` による声の指定はやめる（画面の設定に一本化）。
- **背景・理由**:
  - ユーザーの問い（「動画づくりの依頼に、動画の作成自体を担う役割が必要じゃない？」）に、制作は今もあるが見えていないことを説明し、「工程として見せる」と「声・速さ・BGM を選べる」を合わせる案をユーザーが選んだ。
  - 画像生成 AI に場面の絵を作らせる、など AI に制作の一部を担わせる案は、今の動画テンプレートが図と文字で見せる作りのため、新しい仕組みが要るので今回は採らなかった。
  - 作り直しで声が既定に戻らないよう、動画ごとに設定を残す。
